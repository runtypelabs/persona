# Phase 13 deprecation audit

Audited `v5-defaults-refinements` at `069eb867` (2026-10-12). This is an audit, not an implementation or a removal schedule. No published code was changed. References below are repository paths and line numbers at that revision.

## Recommendation

Do not ship the proposed blanket deprecation of “122 style fields.” The proposed groups include behavior, copy, accessibility, callbacks, independent control styling, and styles with no working theme replacement. A token existing in the type declarations or emitted CSS does not establish that the renderer uses it. No reproducible field list establishes the proposed count.

Limit the first implementation to migration documentation, a small explicit registry of verified aliases, diagnostics on host input, the obsolete demo theme fix, and the generated-config gaps needed for those migrations. Preserve all runtime aliases, exports, CSS aliases, default values, and precedence in both `future.v5Defaults` states throughout 4.x. Keep the larger theme-coverage work separate.

The first blockers to address are:

1. Every snippet format drops `welcome` and `approval`. Moving welcome copy into `welcome` currently loses it on export.
2. Defaulted suggestion aliases still pin chip padding in both states and weight in V4; live `update(undefined)` restores those aliases. A clean theme migration cannot currently stick across updates.
3. Many suggested theme replacements either affect several controls or are unused by the relevant renderer. In particular, ask-user-question has no theme component, and most tool-bubble chrome has no dedicated token.
4. Warning code must examine host input before defaults materialize and must share a stable instance lifetime through updates/rebuilds. Config identity is not a widget lifetime.

## Classification and replacement inventory

“Ready” means the specified ordinary value can be represented for the built-in surface after removing the legacy override; it does not authorize deleting the field. “Keep” means an exact supported migration is absent or incomplete. Theme paths below are relative to `theme`; provide equivalent `darkTheme` overrides where required. A semantic reference changes with the scheme; a literal remains fixed like the old literal config.

## Confirmed tooling and demo gaps

### Generated configs

`utils/code-generators.ts` enumerates supported top-level objects. It emits suggestions, future defaults, theme and old style groups, but has no welcome or approval emission. In-memory bundling/execution of `generateCodeSnippet` confirmed `welcome: { title: "AUDIT_WELCOME" }` and `approval: { backgroundColor: "AUDIT_APPROVAL" }` are absent from **esm, script-installer, script-manual, script-advanced, react-component, react-advanced** outputs. All six preserve `suggestions.followUps`.

The same probe found `copy.showWelcomeCard: false` becomes the string `"false"` in esm, script-manual, react-component and react-advanced. The runtime suppresses the card only for boolean false. This is an existing export defect, relevant to the welcome migration (`code-generators.ts:671–677` and corresponding manual/react branches). Generic fixes must preserve boolean/number types and support serializable welcome/approval fields; function-valued icons/callbacks require an explicit serializer/hooks policy, not JSON dropping them silently.

The editor still authors independent legacy control fields (`theme-editor/sections.ts:915–952`) and pane background (`:1089`). Retain controls for unsupported mappings. For supported mappings, update the editor's target path together with its preview/export tests; otherwise it emits fresh deprecated usage. Existing theme reference and presets also carry those APIs. A default-filled preview export is not proof that the user explicitly selected a legacy field.

### Client-token demo

`apps/web/src/client-token-demo.ts:114–124` supplies `theme.primary/accent/surface/muted/container/border` under `Record<string, unknown>`. `createTheme` only merges palette/semantic/components (`utils/tokens.ts:825`), and `resolveTokens` traverses only those three (`:719–756`). These flat v1 theme values are ignored, not aliases.

The resolver probe supplied flat primary `#090E34` / accent `#3056D3`: both states resolved primary `#171717` / accent `#0f0f0f`, exactly matching no theme input. Fix the demo with a typed `AgentWidgetConfig`/`satisfies` and `theme.semantic.colors: { primary, accent, surface, textMuted, container, border }`; use `textMuted` for old muted. This is a demo correction, not a reason to introduce flat-theme compatibility. Modernize welcome copy/items alongside it only after export/parity conditions are satisfied. Audit-only work did not edit the demo.

## Diagnostics requirements

Add an explicit field registry with a replacement and qualification for each allowed warning. Avoid suffix heuristics, arbitrary recursion over resolved config, warning on object presence, or deprecating whole feature groups. Explicit false/zero/empty strings can carry intent; own undefined resets should not trigger a deprecation warning. Do not compare values with defaults: a host may intentionally choose the default value.

Inspect initial host config and raw live patches before `mergeWithDefaults`; DEFAULTS_BASE itself supplies close/clear background and padding, send border/padding, voice background/borders, and suggestion config. Existing `defaults-provenance` tracks only V5 overlay paths, while `panel-config` tracks geometry aliases. Neither covers every proposed deprecated style. Scanning the post-merge config would warn about almost every untouched widget.

Deduplicate by **widget lifetime plus field path**, keeping state through updates and layout rebuilds; only mark a path as warned when a diagnostic is actually emitted with `debug === true`. Runtime init and UI both merge the same patch (`runtime/init.ts:199–218`; `utils/config-merge.ts:75`), so inserting a logger in both duplicates warnings. The critical launcher and full runtime are separate bundles and identities (`launcher-global.ts:118–146`, deferred installer handoff); choose one ownership boundary or pass shared warning state through the installer. A global module Set alone neither spans the separate bundles nor respects independent widget instances. Preserve the ability for a path first used after mount to warn once.

Welcome WeakSet scoping can warn again after any new config identity and can suppress a newly introduced collision on the same identity. Existing follow-up conflicts use process/module global value signatures and remain unconditional. Preserve those validation diagnostics deliberately or unify them with explicit tests; don't count them as new debug deprecation warnings. CSS usage and arbitrary custom module imports are not observable from raw configuration: document them, never infer usage from emitted vars or warn on package import.

## Suggested implementation order and checks

1. **Export and demo fixes.** Add supported welcome/approval serialization and boolean-copy correctness; fix typed demo theme. Tests should round-trip the affected serializable values through all six formats (evaluate generated config where practical), and assert theme colors reach emitted CSS. This enables a concrete migration result.
2. **Narrow migration release.** Add per-field JSDoc and debug diagnostics for the bounded registry above, complete the existing welcome/follow-up guidance, document compatibility precedence and explicit suggestion placement. Keep aliases/exports unchanged. Migrate generated editor paths only where the replacement is viable. Include a widget patch changeset for published code/type changes; docs/demo alone do not require one.
3. **Separate replacement coverage work.** Design independent header/send/mic tokens, wire approval text/button foreground and voice-state token consumption, provide tool/ask-question/artifact chrome tokens, and solve suggestion-default origin tracking. Introduce these as opt-in theme capabilities so V4 and explicit legacy styling stay stable. Do not couple this to public API removal.

Meaningful focused validation for implementation:

- Parameterize V4 and V5; assert legacy-only behavior, equivalent migrated value, both-key precedence, and unchanged defaults. Include independent close/clear and send/mic values so a shared-token substitute cannot pass by accident.
- Exercise initial input, sparse update, explicit-undefined reset, debug false→true, re-use of raw/defaulted configs, layout rebuild, and two independent instances. Assert no default-triggered warnings, one warning per selected path, and newly introduced paths still warn.
- Check deferred installer first paint/handoff plus eager mounting and standalone approval builders; diagnostics must not double-fire, load a lazy chunk early, or disappear simply because the panel has not opened.
- For suggestions, assert defaulted chip weight/padding precedence and future-toggle behavior, exact placement/variant migration, and empty items. Preserve old follow-up enabled/expose logic and dispatch auto-resume behavior; disabled follow-ups must not advertise the tool.
- Use real computed-style checks for token consumption, hover/focus, stop mode, voice states, and theme switching. Merely asserting that a variable was emitted will miss the confirmed unused-token cases.
- Validate npm/CDN preset exports and approval-ui subpath contracts, public declaration JSDoc, editor preview/export, and plugin hooks receiving supported legacy config. Existing targeted tests include welcome, suggest-replies-tool, config-merge, header-parts, composer-parts, approval-actions/bubble, artifact-gate, tokens and code-generators tests.

## Audit validation performed

Read implementation/types/CSS/resolution/exports/editor/codegen and relevant existing test assertions; ran a small Node 24/esbuild in-memory resolver and codegen probe. No broad suite, build, package mutation, implementation, branch creation, or commit was performed. Resolver probes confirmed the obsolete demo, defaulted suggestion collision/reset behavior, dropped welcome/approval export fields, and quoted legacy welcome boolean. Other replacement conclusions are grounded in the consuming source paths above; browser computed-style parity remains implementation validation, not a claim from this audit. This is a bounded inventory of the proposed groups, not an exhaustive census of every public theme token or third-party integration; unobserved external CSS/plugin consumption prevents declaring public tokens dead.
