Add `features.history.provider`, a public option for supplying your own conversation history backend. Pass a provider instance or a factory (called once per widget instance, so a single script-tag config can back several widgets), and the history UX runs against it in any session mode, including a custom `apiUrl` backend with no client token. Without a provider, history keeps its previous behavior: the built-in Runtype backend, client token mode only. The provider contract is now part of the published types: `HistoryProvider`, `HistoryConversationSummary`, `HistoryConversationPatch`, `PreparedHistoryActivation`, the list, page, and delete-all option shapes, `HistoryOperationContext`, and `HistoryProviderErrorCode`, alongside the `HistoryProviderError` class and the `isHistoryProviderError` guard as value exports reachable from the script-tag global. Providers report failures by throwing `HistoryProviderError` with a `code`: the view branches on that code and never on message text. Optional capabilities stay optional, so a provider without `update` hides the rename and star affordances, and one without `resetDevice` hides "forget this device". Scope resolution respects the provider: the derived default (verified-user with `getIdentityProof`, browser otherwise) narrows to what `capabilities.scopes` advertises, while an explicit `features.history.scope` remains a hard request that fails closed with `unsupported_scope`. Reopening the last conversation after a page reload stays a host concern with a supplied provider: persist the conversation id and call `openConversation` on ready.
