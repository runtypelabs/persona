Support full-duplex (speech-to-speech) voice calls, such as GPT-Live, in the built-in Runtype voice provider. The voice WebSocket now speaks Runtype browser voice protocol v1: it always sends `voiceProtocol=runtype-browser-v1`, `clientVersion=persona/<version>`, `voiceCapabilities=full-duplex-v1`, and the snake_case `clientCapabilities` it supports (`partial_transcript`, `context`, and with client delegation `client_delegation` and `delegation_update`; `attach` on an attach prewarm). It uses only what `session_config.capabilities` confirms, ignores unknown frames, fields and statuses, and keeps the call on an `error` with `fatal: false`. It handles `session_config`, utterance-keyed `transcript_update` (`utteranceId`, falling back to `turnId`), `delegation_started`/`delegation_completed`/`delegation_cancelled`, and `audio_clear` (barge-in) frames. In a speech-to-speech session, reply audio plays continuously, and "speaking" ends when the queued audio has played. A stopped reply is also cancelled on the server.

Voice transcripts that carry a `turnId` are now reconciled by `(turnId, role)`. Each pair keeps one chat bubble that updates in place. Overlapping turns stay separate. A bubble whose transcript carries a `startMs` sorts above any bubble from the same call that started later, so a user transcript that arrives late still renders above the reply it prompted. No empty assistant placeholder is injected; the typing indicator covers the wait. Transcripts without a `turnId` keep the existing alternating behavior. After a stop, a later reply (for example an agent answer that the stop didn't cancel) now gets its bubble while its audio plays.

Client delegation: with the new `voiceRecognition.provider.runtype.clientDelegation` option (default `true`), a full-duplex call hands the agent turns that the voice model delegates to the widget's normal chat pipeline. When the server negotiates `client_delegation`, each `delegation_started` that carries `input` is submitted as the visitor's message, reusing the transcript bubble (`input.userUtteranceIds`) so the request is shown and sent once. The answer streams in as a regular assistant message, with tool and approval UI, WebMCP page tools, and history, and goes back to the voice model as one terminal `delegation_result { delegationId, status, text }` to be read aloud. Its spoken read-back is not added as a second bubble, and browser text-to-speech skips it. After `delegation_cancelled` the widget sends nothing more for that delegation, though the chat turn still renders. In such a call, the voice model's own speech, and anything the visitor said that wasn't submitted, shows as display-only captions (the new `voiceCaption` message flag). Captions are never sent to the agent, so the delegated request is always the last message in the chat request. A turn that arrives while another chat turn is streaming waits for it. Servers that don't negotiate client delegation keep today's server-side behavior. Separately, when the server negotiates `context`, the widget sends the voice model one `context` frame, whether delegation is on or off. The frame holds the chat history as of call start and the new `callContext` option. It is sent when the visitor finishes their first utterance (or at the first delegation, if that comes first). The voice model tends to answer context that arrives earlier: before anyone speaks, or partway through the visitor's sentence. Servers that send no `capabilities` receive neither new frame.

`VoiceProvider` gains an optional `setSessionBridge(bridge)` method, and transcript metadata gains `startMs`, `endMs`, and `caption`. New exported types: `VoiceSessionBridge`, `VoiceDelegationRequest`, `VoiceDelegationResult`, and `VoiceTranscriptMetadata`.

`VoicePlaybackEngine` gains an optional `setContinuousMode(enabled)` method. The provider calls it for speech-to-speech sessions. In continuous mode, the worklet player and `AudioPlaybackManager` release audio held below the prebuffer waterline after one waterline of input silence, so a short reply still plays without an end-of-stream signal. Custom engines without a prebuffer can omit the method.

The realtime provider now re-registers its playback-drained callback for every reply, so later replies also return the status to "listening". `AudioPlaybackManager.flush()` now ignores the late `onended` events of the sources it stopped, so the next reply is no longer reported as finished early.

The Runtype voice provider now captures from the moment the microphone opens instead of waiting for the voice socket. Audio recorded while the socket handshakes is held, capped at 8 seconds with the oldest dropped first, then sent in order once the socket opens. On a slow upgrade, the visitor's first words used to be lost. The held audio is discarded if the call ends, errors, or closes before the socket opens.

Approvals during a full-duplex call: when a delegated turn stops on a tool approval, the widget sends a non-terminal `delegation_update { delegationId, status: 'pending_approval', text }` that explains what is about to happen, so the voice model can ask for the decision in its own words. The text gives each pending tool's name in plain words (`place_pickup_order` becomes "place pickup order"), its description, a short summary of its arguments, and the agent's stated reason, and tells the voice model not to claim the action is done. It is capped at about 1,000 characters. Once the visitor approves or declines in the chat and the resumed turn finishes, the widget sends the outcome as that delegation's one terminal `delegation_result` for the voice model to read aloud. Its read-back is folded like any other. A call that ends first sends nothing. A server without `delegation_update` gets the ask as the result instead.

Voice captions (the voice model's own speech, shown as display-only bubbles) no longer show message actions such as copy. Separately, the default hover action pill no longer covers the end of a short reply. On hover-capable devices, the bubble reserves room for the pill at the end of the last line, or a line below the text when the pill is aligned left or center. This applies to every assistant message.

Approval hardening, for tool approvals that a spoken request raises, both server gates and WebMCP page tools:
- **Status:** every `delegation_result` carries a `status`: `completed`, `denied` (a Deny tap or a spoken decline), `timeout`, `cancelled` (replaced by a newer request), or `failed`. `pending_approval` rides only `delegation_update`. The status set is open.
- **Supersede:** a new pending approval for the same tool declines the earlier one, which closes as `cancelled`, and the voice model says it was replaced. A new spoken request also replaces a pending WebMCP approval instead of waiting behind it.
- **Expiry:** an approval left unanswered for `voiceRecognition.provider.runtype.approvalTimeoutMs` (default 5 minutes) is declined and closes as `timeout`. Hanging up never declines it; the approval card in the chat stays usable.
- **Spoken decline:** while exactly one such approval is pending, an unambiguous spoken decline ("cancel that", "never mind") declines it (`denied`). Nothing is ever approved by voice, and an ambiguous reply runs as a normal turn.
- **AI disclosure:** a speech-to-speech call now shows a one-line AI-disclosure notice in the composer status area: "You're talking to an AI assistant. Voice is processed by OpenAI." Change it with `voiceRecognition.provider.runtype.disclosureText`, or hide it with `false`.
- **API:** `VoiceDelegationRequest` is `{ delegationId, userText, userUtteranceIds, messages }`. `VoiceDelegationResult` is `{ status, text, followUp? }` (no `ok`), and `followUp({ signal, approvalTimeoutMs, readBack })` resolves with the terminal `{ status, text }`, or `null` when the call ends or the server cancels the delegation first. New exported types: `VoiceDelegationStatus` (an open union) and `VoiceDelegationFollowUp`.
