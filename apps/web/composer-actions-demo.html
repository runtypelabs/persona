Three contributors, one row

The paperclip is a core built-in. The clear-draft button comes from composer.actions. The emoji button and the template controls come from two separate plugins. None of them replaces the composer.

Composer actions

One registry, three contributors

Core built-ins, host composer.actions, and every plugin's contributeComposerActions feed a single ordered list. Unlike renderComposer, where the first plugin to return an element wins, every contribution hook runs, so independent plugins coexist.

initAgentWidget({ plugins: [createEmojiQuickInsertPlugin(), createPromptTemplatesPlugin()], composer: { actions: [{ id: "clear-draft", placement: "start", order: 150, label: "Clear the draft", iconName: "x", visible: (state) => state.text.length > 0, onSelect: (ctx) => ctx.setValue(""), }], }, });

Where a control lands

Placement is logical (start or end), never physical, so DOM order and right-to-left layouts agree. Within a cluster, order positions a control against documented anchors. Send is terminal: an end-cluster action ordered at or after 1000 is clamped below it, so nothing can render after send.

// start cluster mention affordances 100 + channel index attachment button 200 // end cluster mic 800 send 1000 // terminal // custom actions default to 500

Ids are namespaced, duplicates are rejected

A plugin action's id becomes <pluginId>:<id> unless it already carries a namespace, so two plugins can both ship a pick action. If two contributors still land on the same final id, the first one wins: core, then host config, then plugins in registry order. The later copy is dropped with a debug warning rather than silently replacing the earlier control.

State drives visibility, not the host

visible and disabled accept a boolean or a predicate over the readonly composer state, and both re-evaluate on every state change and on controller.update(). Type a character and the clear-draft button appears; clear the draft and it leaves. disableWhenStreaming hands the control to the composer's own streaming lock.

Async actions get a busy state

Return a promise from onSelect and the button reports aria-busy until it settles, ignoring repeat activation in the meantime. A rejection is reported through the widget's error path and the button returns to rest. The expand-draft control in this demo waits 600ms on purpose so the state is visible.

{ id: "expand", placement: "end", label: "Expand the draft", onSelect: async (ctx) => { const expanded = await expand(ctx.getValue()); ctx.setValue(expanded); }, }

Custom actions own their markup

A kind: "custom" action returns its own element, which the registry places as the accessible root with nothing wrapped around it. The returned destroy() runs on action removal, composer rebuild, plugin removal, and widget destroy. The template dropdown here is a plain <select>.

{ id: "picker", kind: "custom", placement: "end", order: 600, label: "Prompt templates", render: (ctx) => ({ element, destroy }), }

Capabilities, not internals

An action receives getState, getValue, setValue, submit, openAttachmentPicker, toggleVoice, and requestRender. There is no session and no composer DOM in that context: actions can run before the session exists, so session access would tie a plugin to private lifecycle and transport behavior.

Overflow menu

presentation is already part of the descriptor, with bar, overflow, and auto. This release renders all three in the action row; the overflow menu presentation, with real menu keyboard semantics, lands in a later release over the same registry rather than a second API.
