Presentation

Panel replaces the conversation. Rail is a navigation column beside it. Auto picks per container.

Width is measured on the widget's container, never the viewport. Rail needs at least 720px and collapses to panel below it; auto keeps floating launchers panel-based at every width.

The rail header carries a toggle that shrinks the sidebar to an icon rail, and the choice is remembered for the next visit.

Custom rendering

The toggle mounts a thread rail plugin built on public hooks only. When its renderHistoryView returns an element, the built-in Messages view never renders.

Persona still owns chunk loading, placement, Escape and focus, and the destructive confirmations. One renderer covers both placements; switch presentation to rail to see it beside an operable transcript.

With the toggle off, a second plugin contributes a pinned section through railSections instead of replacing the view. Its markup and styles are host-side, and it renders nothing while the rail is collapsed. Switch presentation to rail to see it above the conversation list.

Identity status

Injects the identity state the real provider would report. The scope line in Messages reflects only reported evidence, never a configured callback.

Open Messages after injecting a failing state: an unavailable account scope explains itself instead of rendering an apparently empty browser list.

Loading and errors

Latency drives the skeletons. Failures are one-shot per operation: the next call fails, the retry succeeds.

Failing the replacement init after an irreversible delete is what produces the new_conversation_required recovery state: queue "Fail next new conversation", then delete the open conversation.

Delete and empty

Deleting an inactive row is non-disruptive. Deleting the open one is irreversible, so the transcript is replaced rather than restored.

Forget this device

This provider has no resetDevice, so the control never renders and the controller method rejects. Reset is a visitor-credential operation, not a generic history one.

Messages, end to end

Two sources, one surface

The same Messages surface runs against two sources.

  • In-memory: a deterministic demo provider, so every state on this page is reachable without a network.
  • Live API: the widget builds the real provider from a client token and runs the identical surface against the Runtype API.

Page code never touches a provider. Every action goes through controller methods and the widget's own view.

initAgentWidget({ config: { clientToken, apiUrl, features: { history: { enabled: true, presentation: "panel" } }, } });

Panel, rail, and auto

Three placements, resolved against the host container width.

  • Panel (default): Messages replaces the conversation body and composer, and both become inert, so a visitor can never send into the conversation hidden underneath.
  • Rail: the transcript and composer stay operable beside a navigation column, and selecting a conversation keeps the rail open.
  • Auto: resolves to rail only for a wide inline or docked shell.
  • Below 720px, rail and auto both collapse to panel rather than squeezing either surface.

States covered here

  • Identity: browser only, verifying, verified, authentication required, identity provider failed, and proof not admitted.
  • List: loading skeletons, ready, confirmed empty, error with retry, and the 429 soft state with its retry-after wait.
  • Recovery: new_conversation_required, after an irreversible delete whose replacement init failed.
  • Destructive: delete one, delete all for the active target, and the hidden forget-this-device control.

Live API setup

The live source reads apps/web/.env. With the token missing, the page shows setup instructions instead of a broken widget.

  • VITE_CLIENT_TOKEN_HISTORY: a client token with visitor history enabled. Tokens are origin-locked in the Runtype dashboard; allow http://localhost:5173 and http://localhost:4173 for local work.
  • VITE_HISTORY_API_URL (optional): defaults to https://api.runtype.com. Point it at a staging host to test unreleased contract changes.

Custom rendering

Four public render hooks arbitrate around the default view. Every hook may return null to fall through, and a hook that throws is reported and falls back rather than losing the surface.

  • renderHistoryView: replaces the whole view.
  • renderHistoryHeader: replaces the top bar.
  • renderHistoryConversation: replaces one row.
  • renderHistoryState: replaces a non-ready list state.

The "Custom thread rail" toggle mounts a plugin that returns its own DOM from renderHistoryView.

  • It reads the frozen context snapshot: conversations, active id, list state, pending action, resolved presentation, copy.
  • It calls context.actions for every operation, so busy gating, selection epochs, and the destructive confirmations behave exactly as the built-in view.
  • The snapshot carries no provider, credential, or transport detail.

A host that wants navigation entirely outside the widget shell can build it headlessly with controller methods and history:* events.
