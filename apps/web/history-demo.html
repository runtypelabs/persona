Identity status

Injected through the demo provider, exactly as the Runtype provider would report it from init and per-response acknowledgement. The scope line under the Messages heading is evidence-based: it never infers verification from a configured callback.

Open Messages after injecting a failing state: an unavailable account scope explains itself instead of rendering an apparently empty browser list.

Loading and errors

Latency drives the skeleton state; the failure queue is one-shot per operation, so the next call fails and the retry succeeds.

Failing the replacement init after an irreversible delete is what produces the new_conversation_required recovery state: queue "Fail next new conversation", then delete the open conversation.

Delete and empty

Deleting an inactive row is non-disruptive; deleting the open one is irreversible, so the transcript is replaced rather than restored.

Forget this device

The in-memory provider has no resetDevice, so the destructive footer never renders that control and the controller method rejects as misuse. Reset is a Runtype visitor-credential operation, not a generic history one.

Messages, end to end

Two sources, one surface

The in-memory source mounts a deterministic provider through the source-only internal registry, so every state on this page is reachable without a network. Live staging drops the override and lets the widget build the Runtype provider from a client token, which exercises the same core Messages surface against a real visitor plane. Neither source touches a provider from page code: all actions go through the controller methods and the widget's own view.

initAgentWidget({ config: { clientToken, apiUrl, features: { history: { enabled: true, presentation: "panel" } }, } });

Panel, rail, and auto

Panel is the default: Messages replaces the conversation body and composer, both of which become inert, so a visitor browsing history can never send into the conversation hidden underneath. Rail keeps the transcript and composer operable beside a navigation column and stays open when a conversation is selected. Auto resolves to rail only for a wide inline or docked shell. Below 720px of host container width, rail and auto both collapse to panel rather than squeezing either surface.

States covered here

  • Identity: browser only, verifying, verified, authentication required, identity provider failed, and proof not admitted.
  • List: loading skeletons, ready, confirmed empty, error with retry, and the 429 soft state with its retry-after wait.
  • Recovery: new_conversation_required, after an irreversible delete whose replacement init failed.
  • Destructive: delete one, delete all for the active target, and the hidden forget-this-device control.

Live staging setup

Live staging reads two variables from apps/web/.env: VITE_HISTORY_API_URL and VITE_CLIENT_TOKEN_HISTORY. With either missing, the page shows setup instructions instead of a broken widget.

Phase 0 of the history contract is deployed to the staging API only, not to api.runtype.com, so this demo refuses to run when the URL points at production. The staging token is origin-locked to http://localhost:5173 and http://localhost:4173, so it works on the dev server and a local preview build and nowhere else.

Custom rendering

The plan's public render hooks (renderHistoryView, renderHistoryHeader, renderHistoryConversation, renderHistoryState) are not on the plugin interface yet, so the ChatGPT-style rail here is the built-in view under presentation: "rail". When those hooks land, a custom full-view renderer becomes a fourth source on this page. A host that wants navigation outside Persona's shell can already build it headlessly today with the controller methods and history:* events.
